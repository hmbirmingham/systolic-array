Cortex-M4 baseline for the 4x4 homogeneous transform
=====================================================

Not a CI figure. There is no board on the runner, so unlike the transform and
synthesis numbers this one cannot be regenerated by a workflow. It is a board
run, recorded here so the README figure has a source.

Measured   2026-11-25
Part       STM32F411RE  (chipid 0x431, 128 KiB SRAM, 512 KiB flash)
Probe      ST-LINK V2J33M25
Clock      16 MHz HSI, reset default. No PLL, no flash prefetch, no ART.
           DWT->CYCCNT counts core clocks, so cycles/point does not depend on
           the clock. Wall-clock would.
Compiler   arm-none-eabi-gcc (GCC) 16.2.0
Flags      -mcpu=cortex-m4 -mthumb -O2 -std=c11 -ffreestanding -fno-common
Firmware   bench/mcu/, 496 bytes text
Reproduce  cd bench/mcu && make flash read

Derived
-------
                        cycles    /tile   /point   /MAC
naive C (rolled k)     206,850    808.0   202.00  12.63
optimised C (unrolled)  92,161    360.0    90.00   5.63
loop overhead            2,309      9.0

64 multiply-accumulates per tile, 4 points per tile, 16 MACs per point.
Overhead is a pass over the same tiles with no transform, subtracted from both.

Why two variants
----------------
The naive version leaves the k loop rolled. gcc emits SMLABB, the M4's
single-cycle multiply-accumulate, but each one also pays two loads, a compare
and a taken branch, and the M4 has no branch predictor. 12.63 cycles per MAC is
consistent with that code rather than evidence of a bad compile.

The optimised version unrolls k and hoists the point's four components into
locals, which removes the inner branch and cuts the point loads fourfold.
2.24x faster. Comparing the array against the naive figure would flatter the
array, so the README quotes the optimised one.

An earlier run measured 220.8 cycles/point because the timed region also built
the input tiles, with a multiply and a modulo per element. 13.8 cycles per MAC
on a core with a one-cycle MAC was the tell. Inputs are now built before timing.

Correctness
-----------
Both C variants agree with each other and with golden/transform_ref.py bit for
bit over 32 tiles: realistic transform data, the full-scale signed corners, the
single-term 2^30 corner, and random full-range tiles.

    .venv/bin/python bench/mcu/crosscheck.py

That makes the C a second implementation of the format, not only a baseline.
The Python model was previously trusted for being short; now something checks
it.
